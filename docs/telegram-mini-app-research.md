# Mini App для Listik-bot

Дата исследования: 2026-09-23.

## Вывод

Listik-bot можно постепенно дополнить полноценным Telegram Mini App без переноса существующей бизнес-логики в браузер. Рекомендуемый вариант:

```text
Telegram Mini App
        │ HTTPS + initData
        ▼
HTTP API в том же приложении
        │
        ▼
Сервисный слой списка/шаблонов/комнат
        │
        ▼
SQLite
```

Открывать приложение следует через кнопку меню бота с помощью `setChatMenuButton`. Для первого релиза оставляем polling для Telegram-бота и поднимаем FastAPI, HTTP API и WebSocket в том же приложении; PostgreSQL запускаем отдельным контейнером в текущем Docker Compose. Frontend строим на React, Vite и TypeScript.

## Что есть в текущем проекте

Подтверждено по исходникам:

- `bot.py` запускает только aiogram Dispatcher в polling-режиме; отдельного HTTP-сервера и web-клиента нет.
- `pyproject.toml` содержит aiogram, aiosqlite и Pydantic, но не содержит FastAPI, Starlette или frontend toolchain.
- `handlers.py` содержит UI и orchestration в одном крупном модуле: reply-клавиатуры, inline callbacks и FSM для добавления товара, шаблонов и комнат.
- `database.py` уже поддерживает комнаты, участников, активную комнату пользователя, товары, категории, купленные товары и шаблоны.
- В БД есть `room_id` у товаров и шаблонов, а операции чтения списка и шаблонов умеют принимать `room_id`.
- Docker Compose запускает один контейнер бота и сохраняет SQLite в volume `./data`.
- `models.py` не объявляет `room_id` в `Item` и `Template`; при создании API-моделей это поле нужно добавить явно, иначе оно не попадёт в стандартную сериализацию Pydantic.

Следствие: слой данных уже близок к нужному домену, но бизнес-операции сейчас вызываются непосредственно из Telegram handlers. Для Mini App нужен отдельный HTTP boundary и общие сервисные функции, чтобы Telegram UI и web UI не дублировали правила доступа и обработки конфликтов.

## Как Telegram запускает Mini Apps

Telegram поддерживает запуск Mini App из keyboard button, inline button, menu button, профиля бота, direct link и других контекстов. Для этого продукта подходят два способа:

1. **Кнопка меню бота** — основной способ. Пользователь открывает приложение из чата, а Mini App получает `Telegram.WebApp.initData` с данными текущего пользователя.
2. **Inline-кнопка или reply-кнопка** — полезно как запасной путь для первого эксперимента или deep link на конкретный экран.

`sendData` не стоит использовать как основной транспорт для списка: он предназначен для передачи строки обратно боту через service message. Для полноценного интерактивного приложения Telegram рекомендует Mini App, который обращается к собственному backend API.

На стороне клиента подключается официальный скрипт:

```html
<script src="https://telegram.org/js/telegram-web-app.js"></script>
```

На стороне сервера необходимо принимать сырое значение `Telegram.WebApp.initData`, проверять HMAC-SHA-256 через токен бота и дополнительно проверять свежесть `auth_date`. `initDataUnsafe` нельзя использовать как источник доверенной авторизации. После проверки backend получает Telegram ID и уже по нему применяет существующие правила одобрения и членства в комнате.

## Предлагаемый пользовательский интерфейс

Главный экран Mini App:

- верхняя панель с названием активной комнаты и переключателем комнат;
- счётчик «осталось купить»;
- строка быстрого добавления товара;
- список товаров по категориям супермаркета;
- чекбокс или swipe-жест для отметки «куплено»;
- нижняя навигация: «Список», «Шаблоны», «Комната», «Ещё».

Поведение списка:

- добавление начинается с быстрого ввода названия, меры и количества; категория определяется автоматически, а при неуверенной классификации Mini App просит выбрать её вручную;
- изменение количества выполняется прямо в карточке товара;
- удаление и очистка купленного требуют нативного подтверждения Telegram или modal confirmation;
- фильтры: «Все», «Купить», «Куплено», категория;
- после каждого действия Mini App запрашивает актуальное состояние через API, а не перерисовывает Telegram-сообщения;
- полноценный offline-first режим и очередь несинхронизированных команд в первую миграцию не входят.
- для открытой комнаты нужен realtime-канал: изменение одного участника должно приходить другим участникам без ручного обновления.
- при reconnect WebSocket клиент автоматически переподключается с backoff и делает полный refetch списка; незавершённый ввод в форме не теряется и не повторяется молча.

Экран «Шаблоны»:

- карточки шаблонов с количеством товаров;
- просмотр и редактирование состава;
- действие «Добавить в список»;
- отдельный экран разрешения конфликтов с решением по каждой позиции; доступны объединение количества, замена значения, сохранение текущего значения и отмена. Перед применением показывается итоговое preview, а выбранные решения сохраняются одной транзакцией.

Экран «Комната»:

- текущая комната и список доступных комнат;
- создание, переименование и удаление для создателя;
- приглашение участника и управление членами;
- явное отображение роли пользователя.

Для интерфейса нужно использовать theme-переменные Telegram, поддержать светлую и тёмную тему, safe area и mobile-first layout. Основные действия удобно связывать с нижней `BottomButton`, а системную кнопку Back — с маршрутизацией Mini App.

Выбранный визуальный вектор — яркий grocery-интерфейс: заметный акцентный цвет, выразительные категории и живые состояния списка, но с адаптацией к светлой и тёмной теме Telegram. Яркость не должна превращаться в перегруженный dashboard: главным объектом остаётся список и действие «куплено».

Выбрана цветовая система «свежий grocery»: зелёный/лаймовый основной цвет, коралловые акценты и мягкие фоны с отдельной адаптацией для тёмной темы.

## Архитектурные варианты

| Вариант | Подходит | Плюсы | Минусы |
|---|---|---|---|
| `sendData` + существующие handlers | Простая форма ввода | Почти нет backend-изменений | Нет полноценного списка, неудобна синхронизация и редактирование |
| Отдельный frontend + HTTP API в текущем приложении | Выбранный вариант | Нормальный UI, одна бизнес-логика и одна БД | Потребуется API, auth, WebSocket и сборка frontend |
| Отдельный frontend + отдельный backend-сервис | Дальнейшее развитие | Чёткое разделение и независимый deploy | Сложнее deploy, auth, миграции и работа с SQLite |

Для текущего размера проекта отдельный backend-сервис преждевременен. Делаем один deployable unit с polling aiogram, FastAPI, HTTP API, WebSocket и static hosting; PostgreSQL остаётся отдельным контейнером с persistent volume и закрытым сетевым доступом. SQLAlchemy Async и Alembic становятся общей основой доступа к данным и миграций.

## API-контракт MVP

Все endpoint-ы требуют проверенный `initData`. `room_id` из клиента нельзя считать доверенным: сервер проверяет, что пользователь состоит в комнате.

```text
GET    /api/v1/me
GET    /api/v1/rooms
POST   /api/v1/rooms
POST   /api/v1/rooms/{room_id}/select

GET    /api/v1/rooms/{room_id}/items
POST   /api/v1/rooms/{room_id}/items
PATCH  /api/v1/rooms/{room_id}/items/{item_id}
POST   /api/v1/rooms/{room_id}/items/{item_id}/purchase
DELETE /api/v1/rooms/{room_id}/items/{item_id}
POST   /api/v1/rooms/{room_id}/items/clear-purchased

GET    /api/v1/rooms/{room_id}/templates
GET    /api/v1/rooms/{room_id}/templates/{template_id}
POST   /api/v1/rooms/{room_id}/templates/{template_id}/apply

GET    /api/v1/rooms/{room_id}/members
POST   /api/v1/rooms/{room_id}/members/invite
```

Ответы должны быть JSON-моделями с единым форматом ошибки. Операции изменения — идемпотентными там, где это возможно, и должны повторно проверять доступ непосредственно перед записью. Добавление товара с совместимой единицей должно атомарно объединять количество; ручное редактирование должно передавать версию объекта и получать конфликт при устаревшем состоянии.

WebSocket передаёт событие-инвалидатор с комнатой, типом изменения, сущностью, идентификатором и версией. Клиент после события делает refetch через HTTP API; после reconnect выполняется полный refetch. Существующие числовые ID сохраняются при импорте в PostgreSQL.

## Что нужно изменить в backend

1. Вынести из `handlers.py` сервисные операции списка, шаблонов и комнат. Telegram handlers будут вызывать эти сервисы, а HTTP endpoints — те же сервисы.
2. Добавить функцию валидации Telegram `initData` с ограничением срока действия и тестами на неверный hash, просроченные данные и отсутствие пользователя.
3. Добавить HTTP-приложение и конфигурацию `MINI_APP_URL`.
4. Явно добавить `room_id` в `Item` и `Template` или завести отдельные response-модели для API.
5. Усилить авторизацию DB-операций: `mark_as_purchased`, `remove_item`, `update_item_quantity` и операции шаблонов должны проверять принадлежность объекта указанной комнате, а не принимать только числовой ID.
6. Добавить endpoint health/readiness и reverse proxy с HTTPS.
7. Настроить PostgreSQL и миграцию данных: остановить запись, сделать backup SQLite, импортировать данные в PostgreSQL через Alembic/SQLAlchemy, выполнить smoke-тесты и только затем переключить конфигурацию. SQLite убрать из runtime, сохранив исходный файл как архивный backup на период отката.
8. На старте бота настроить кнопку меню:

Realtime нужен для товаров активной комнаты. События шаблонов, комнат и участников в первую миграцию не входят: эти данные обновляются при открытии соответствующего экрана и после собственных действий.

Навигация Mini App: «Список», «Шаблоны», «Комнаты», «Ещё». Добавление и редактирование открываются как bottom sheet/modal поверх контекста, а не как отдельный набор чатов или сообщений.

```python
from aiogram.types import MenuButtonWebApp, WebAppInfo

await bot.set_chat_menu_button(
    menu_button=MenuButtonWebApp(
        text="Открыть список",
        web_app=WebAppInfo(url=settings.mini_app_url),
    )
)
```

## План реализации

### Фаза 1 — вертикальный срез

- добавить frontend с экраном списка;
- добавить auth через `initData`;
- реализовать `GET items`, добавление товара и отметку купленным;
- подключить кнопку меню;
- проверить работу в Telegram на светлой и тёмной теме.

### Фаза 2 — перенос основных функций

- комнаты и переключение активной комнаты;
- шаблоны и применение шаблона;
- редактирование и удаление товаров;
- синхронизация после действий и обработка ошибок сети.

### Фаза 3 — переход данных и hardening

- оставить старые команды и клавиатуры как fallback;
- перенести рабочие данные из SQLite в PostgreSQL в согласованное окно cutover;
- добавить API contract tests и frontend smoke tests;
- проверить права для пользователя из другой комнаты;
- добавить аудит ошибок API и latency.

Перед production-переключением приемка должна подтвердить семь обязательных сценариев в старом боте и Mini App на одной базе, включая двух участников одной комнаты, запрет доступа к чужой комнате, reconnect WebSocket, конфликт ручного редактирования, применение шаблона и восстановление из backup.

Рабочая SQLite-база признана практически пустой, поэтому перенос legacy-записей с `room_id IS NULL` не требуется. После backup и проверки cutover старую SQLite можно убрать из runtime и не поддерживать отдельный legacy-режим. Приглашение в первой миграции остаётся по `@username`; invite link не входит в scope.

## Риски

- **Доверие к клиенту.** Нельзя принимать Telegram ID, `room_id` или права из JSON Mini App без серверной проверки.
- **Параллельные изменения.** Два участника могут одновременно отметить или изменить товар; endpoint должен корректно обрабатывать уже изменённую запись и возвращать актуальное состояние.
- **Переход базы.** Прямой cutover без окна остановки записи может потерять изменения. Нужны backup, импорт, smoke-тесты и только после этого переключение источника истины на PostgreSQL.
- **Смешение UI и домена.** Если копировать код `handlers.py` в API, правила комнат и конфликтов быстро разойдутся. Сначала нужен сервисный слой.
- **Деплой.** В production Mini App должен быть доступен по HTTPS; отдельный арендованный домен Telegram не требует. При наличии публичного IP можно использовать HTTPS непосредственно на IP-адресе: Let’s Encrypt с 2026 года поддерживает публично доверенные IP-сертификаты, но они действуют около шести дней, поэтому автоматическое продление обязательно. Для разработки подойдёт tunnel.
